# ADR-005: Built-in Agent SDK tools behind a per-role PreToolUse policy; GitHub only through `gh` in non-agent code

**Status:** Accepted (2026-11-15)
**Decision area:** D5, tools

## Context

Agents need to read the repository, some need to edit files and run tests. Nothing in the
six stages requires an *agent* to talk to GitHub: pushing, opening a PR, posting a review
are all mechanical. Each tool an agent holds is also something a prompt injection can use.

## Decision

- Agents run on the **Claude Agent SDK** (`claude-agent-sdk` 0.2.182) with built-in tools.
  The available tools per role are fixed by `ClaudeAgentOptions.tools`:

  | Role | Tools |
  |---|---|
  | Planner | Read, Glob, Grep |
  | Implementer | Read, Glob, Grep, Edit, Write, Bash |
  | Tester | Read, Glob, Grep, Edit, Write, Bash |
  | Reviewer | Read, Glob, Grep, Bash, Write |

- A **`PreToolUse` hook** (`policy.py`, `on_failure="block"`) decides every call:
  - Read/Glob/Grep: only inside the work directory, never `.git/`.
  - Edit/Write: implementer only on paths listed in `design.md` outside `tests/`,
    `.github/`, `.autose/`; tester only on `tests/test_autose_issue_N.py`; reviewer only
    inside its scratch directory.
  - Bash: a per-role allowlist of command prefixes (`python -m pytest`, `python -m compileall`,
    `git diff`, `git status`, `ls`, …), no pipes to the network, no `git push`, no `curl`.
    Bash runs in the SDK **sandbox** (bubblewrap) with no network access.
  - Everything else: deny. `permission_mode="dontAsk"` makes any undecided call fail closed.
- `setting_sources=[]` so project or user settings in the checked-out repository cannot add
  tools, hooks or permissions.
- **No MCP servers, no WebFetch/WebSearch.**
- **GitHub access** is only through the `gh` CLI, called by `gate.py`, `release.py`,
  `store.py` and `publish.py`, with the job's `GITHUB_TOKEN` passed explicitly to those
  subprocesses. The token is removed from `os.environ` before any agent starts, and
  `actions/checkout` runs with `persist-credentials: false`.

## Alternatives considered

- **GitHub MCP server for agents.** Popular, but it puts a write-capable token inside the
  agent process and exposes dozens of tools we would then have to filter.
- **`can_use_tool` callback only.** It is not consulted for calls the CLI already treats as
  safe (reads), so path restrictions on reads would not hold. The hook sees every call.
- **No Bash at all.** Then the implementer and tester could not run tests, and the
  "the code builds / tests pass" checks would only happen after the agent was done, making
  every failure a full extra round.

## Consequences

- The policy is about 150 lines of code that we can unit-test without a model.
- Agents sometimes waste turns on denied commands; denials are logged and counted per run.
- Sandboxing depends on bubblewrap and unprivileged user namespaces on the runner
  (Ubuntu 24.04 needs one `sysctl`). If the sandbox cannot start, the run stops rather than
  running Bash unsandboxed.
