# ADR-011: Agent Bash runs in our own bubblewrap jail, applied by the permission hook

**Status:** Accepted (2026-11-15). Replaces the "Agent Bash runs sandboxed without network" point
of [ADR-009](ADR-009.md) and the Bash sandbox point of [ADR-005](ADR-005.md); the rest of both
still holds.
**Decision area:** D9, safety and failures (also D5, tools)

## Context

ADR-009 relied on the Claude Agent SDK's built-in Bash sandbox (`sandbox.enabled`, no allowed
domains) to cut agent commands off from the network. The first real run on issue #1
([run 43716337981](https://github.com/iDheer/tinydb/actions/runs/43716337981)) showed that this
sandbox doesn't start on a GitHub-hosted Ubuntu runner. Every command failed with
`apply-seccomp: write /proc/self/setgroups: Permission denied`. The implementer made the right
one-line change, couldn't run a single test, and reported `blocked`. Plain bubblewrap, on the
other hand, works on the same runner (the workflow's probe step passed).

## Decision

- The SDK sandbox is turned off. Instead, the PreToolUse hook that already approves every tool
  call (ADR-005) **rewrites every allowed Bash command** (`updatedInput`) so that it runs under
  `bwrap` with:
  - no network (`--unshare-net`);
  - its own PID and IPC namespaces and a fresh `/proc`, so the orchestrator, the key proxy and
    their environments are invisible;
  - the whole filesystem read-only, except the work tree, the reviewer's scratch folder and an
    empty `/tmp`;
  - `$RUNNER_TEMP` hidden.
- The policy checks the command first and rejects shell metacharacters, so the rewritten
  command is exactly the allowed one with a fixed prefix in front. The verdict rules (ADR-008)
  still see the original command.
- If `bwrap` can't run, the prefix falls back to `unshare -rn` (cuts the network only), and the
  log says so.
- A related fix from the same run: when the implementer reports `blocked`, the run no longer
  stops before the stage-3 check. Agents propose and checks decide (ADR-002), so the check runs
  anyway, and only its result moves the state machine.

## Alternatives considered

- **`enableWeakerNestedSandbox`.** The SDK option meant for unprivileged containers. It weakens
  the isolation, and what exactly it weakens isn't documented clearly enough to rely on.
- **No sandbox, just the command allowlist.** `python -c` and `pytest` can run any code, so an
  allowlist alone would leave the network and the orchestrator's files open.
- **Run the whole CLI inside a network namespace.** It would then need a socket bridge to reach
  the key proxy. That's more moving parts than wrapping each command.

## Consequences

- The jail is our own code (about 25 lines) instead of the SDK's, so testing it is on us: a unit
  test checks the rewrite, and the workflow tries the exact `bwrap` flags before the
  orchestrator starts.
- The filesystem is stricter than before. Agent commands can no longer write to the `.autose/`
  copies or the control checkout, even with `python -c`.
- Commands can still read system files and the runner's home folder. Nothing secret is kept
  there (the checkouts don't save credentials).
