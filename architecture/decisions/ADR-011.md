# ADR-011: Agent Bash runs in our own bubblewrap jail, applied by the policy hook

**Status:** Accepted (2026-11-15). Supersedes the "Agent Bash runs sandboxed without network"
point of [ADR-009](ADR-009.md); the rest of ADR-009 stands.
**Decision area:** D9, safety and failures (also D5, tools)

## Context

ADR-009 relied on the Claude Agent SDK's built-in Bash sandbox (`sandbox.enabled`,
no allowed domains) to give agent commands no network. The first real run on issue #1
([run 43716337981](https://github.com/iDheer/tinydb/actions/runs/43716337981)) showed that
this sandbox does not start on a GitHub-hosted Ubuntu runner: every command failed with
`apply-seccomp: write /proc/self/setgroups: Permission denied`. The implementer made the
correct one-line change, could not run any test, and reported `blocked`. Plain bubblewrap
does work on the same runner (the workflow's probe step passed).

## Decision

- The SDK sandbox is switched off. Instead, the PreToolUse hook that already decides every
  tool call (ADR-005) **rewrites every allowed Bash command** (`updatedInput`) to run under
  `bwrap` with: no network (`--unshare-net`), its own PID and IPC namespaces and a fresh
  `/proc` (the orchestrator, the key proxy and their environments are invisible), the whole
  filesystem read-only except the work tree, the reviewer's scratch directory and an empty
  `/tmp`, and `$RUNNER_TEMP` hidden.
- The policy checks the command first and rejects shell metacharacters, so the rewritten
  argv is exactly the allowed one with a fixed prefix; the verdict rules (ADR-008) still see
  the original command.
- If `bwrap` cannot run, the prefix falls back to `unshare -rn` (network only) and the log
  says so.
- Related fix from the same run: an implementer's `blocked` status no longer stops the run
  before the stage-3 check. Agents propose and checks decide (ADR-002), so the check runs and
  only its result moves the state machine.

## Alternatives considered

- **`enableWeakerNestedSandbox`.** The SDK option meant for unprivileged containers. It
  weakens isolation, and what it weakens is not documented clearly enough to rely on.
- **No sandbox, policy allowlist only.** `python -c` and `pytest` run arbitrary code, so an
  allowlist alone leaves the network and the orchestrator's files open.
- **Run the whole CLI inside a network namespace.** It would then need a socket bridge to
  reach the key proxy. That is more moving parts than wrapping each command.

## Consequences

- The jail is our code (about 25 lines) instead of the SDK's, so it is ours to test: a unit
  test checks the rewrite, and the workflow probes the exact `bwrap` flags before the
  orchestrator starts.
- The filesystem is stricter than before: agent commands can no longer write to
  `.autose/` copies or the control checkout, even with `python -c`.
- Commands still see read-only system files and the runner's home directory; nothing secret
  is stored there (no credentials are persisted by the checkouts).
