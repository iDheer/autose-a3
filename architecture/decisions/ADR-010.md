# ADR-010: A maintainer's label or `/autose` comment starts a run; one queue per issue

**Status:** Accepted (2026-11-15)
**Decision area:** D10, triggers

## Context

The assignment's sketch uses `issues: labeled` and `issue_comment: created`. Both events fire for
*everyone*: every comment on every issue and PR starts the workflow. Who is allowed to trigger
it matters, because a run costs money and writes to the repo. Runs can also collide: a
maintainer adds the label and comments `/autose` at the same time, or comments again while a run
is still going.

## Decision

Triggers:

| Event | What `gate.py` checks | What happens |
|---|---|---|
| `issues: labeled` | the label is `autose` (only people with triage rights or more can add labels) | start from stage 1 |
| `issue_comment: created` on an issue | the comment starts with `/autose`, `author_association` is OWNER, MEMBER or COLLABORATOR, and the author isn't a bot | start from stage 1 (restarting is allowed, and the maintainer's answers to stage-1 questions are included) |
| `issue_comment: created` on an `autose/issue-N` PR | `/autose review`, same author rule | one more review round, if the budget allows |
| `workflow_dispatch` | needs write access; used by `publish.py` for rework rounds and by me for the experiments | `mode=rework|review` with explicit inputs |

Anything else ends in the `gate` job within seconds, without checking out code or touching
secrets.

**No collisions:** `concurrency: group: autose-issue-N, cancel-in-progress: false`. A second
trigger for the same issue waits for the first one to finish instead of racing it on the same
branch. GitHub keeps only one *waiting* run per group, so a third trigger replaces the waiting
second one. That's what I want for repeated `/autose` comments. Different issues run in
parallel; the only thing they share is the artifacts branch, which pushes with rebase and retry
(ADR-004).

## Alternatives considered

- **Label only.** Simplest, but answering stage-1 questions or restarting a run would mean
  removing and re-adding the label.
- **Anyone can comment `/autose`.** Then outsiders could spend the maintainers' money and inject
  text whenever they like.
- **`cancel-in-progress: true`.** A newer command would kill a run in the middle of stage 5,
  leaving a pushed branch with no PR.

## Consequences

- `issue_comment` still starts a (cheap) workflow run for every comment in the repo. The gate
  job ends it within a few seconds.
- Workflows started from forks of *our* fork don't get secrets, so an outsider's PR can never
  start an agent run. Only issues can, and only after a maintainer acts.
