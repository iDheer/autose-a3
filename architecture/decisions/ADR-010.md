# ADR-010: Label or `/autose` from a maintainer starts a run; one queue per issue

**Status:** Accepted (2026-11-15)
**Decision area:** D10, triggers

## Context

The assignment's sketch uses `issues: labeled` and `issue_comment: created`. Both events fire
for everyone's activity: every comment on every issue and PR starts the workflow. Who is allowed
to trigger matters because the run spends money and writes to the repository. Runs can also
collide: a maintainer adds the label and comments `/autose` at the same time, or comments again
while a run is in progress.

## Decision

Triggers:

| Event | Condition checked in `gate.py` | Effect |
|---|---|---|
| `issues: labeled` | label is `autose` (only users with triage rights or more can label) | start from stage 1 |
| `issue_comment: created` on an issue | body starts with `/autose`, `author_association` ∈ {OWNER, MEMBER, COLLABORATOR}, author is not a bot | start from stage 1 (restarts are allowed, and maintainer answers to stage-1 questions are included) |
| `issue_comment: created` on an `autose/issue-N` PR | `/autose review`, same author rule | one more review round if the budget allows |
| `workflow_dispatch` | needs write access; used by `publish.py` for rework rounds and by us for experiments | `mode=rework|review` with explicit inputs |

Everything else ends in the `gate` job within seconds, without checking out code or reading
secrets.

Concurrency: `concurrency: group: autose-issue-N, cancel-in-progress: false`. A second
trigger for the same issue waits for the first to finish instead of racing on the same
branch. GitHub keeps only one *pending* run per group, so a third trigger replaces the pending
second one, which is the behaviour we want for repeated `/autose` comments. Different issues run in
parallel; their only shared resource is the artifacts branch, which uses a rebase-and-retry
push (ADR-004).

## Alternatives considered

- **Label only.** Simplest, but answering stage-1 questions and re-triggering would mean
  removing and re-adding labels.
- **Any commenter.** Lets outsiders spend the maintainers' money and inject text at will.
- **`cancel-in-progress: true`.** A newer command would kill a run halfway through stage 5,
  leaving a pushed branch without a PR.

## Consequences

- `issue_comment` still starts a (cheap) workflow run for every comment in the repository; the
  gate job stops in a few seconds.
- Workflows triggered from forks of *our* fork do not get secrets, so a PR from an outsider
  can never start an agent run; only issues can, after a maintainer acts.
