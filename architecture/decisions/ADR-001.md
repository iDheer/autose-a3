# ADR-001: Four agent roles, split by what each one is allowed to do

**Status:** Accepted (2026-11-15)
**Decision area:** D1, splitting the work

## Context

The workflow has six fixed stages. They don't just need different inputs, they need
different *permissions*. Writing a spec or a design only needs to read the code. Implementing
needs to write source files. Testing needs to write a test file and run code. Reviewing has to
be independent of all of that. Stage 5 (push, open a PR, wait for CI) is pure mechanics, so
there is nothing for a model to decide there.

Two lessons from A2 pushed me here. The agent worked best when it got one small, clear task
with a clear way to check it. And one long session slowly fills up with old tool output and
failed attempts, which later stages don't need and which make the agent stick to its first idea.

## Decision

I use **four agent roles** and one extra model call that is not an agent:

| Role | Stages | Model | Can write |
|---|---|---|---|
| Planner | 1 Requirements, 2 Design (two separate, fresh sessions) | Sonnet 5.5 | nothing, it returns structured output |
| Implementer | 3 Implementation | Sonnet 5.5 | the source files named in `design.md` |
| Tester | 4 Testing | Sonnet 5.5 | only `tests/test_autose_issue_N.py` |
| Reviewer | 6 Review | Opus 5.5 | a scratch folder outside the repository |
| (testability judge) | the check after stage 1 | Haiku 5.5 | nothing, no tools |

Stage 5 is ordinary code (the release step `st_release` in `orchestrator.py`), not an agent.

The line between roles is drawn where the **permissions** change, not where the stages
change:
- Stages 1 and 2 share the Planner role because they need the same rights (read-only) and the
  same knowledge (the repo and `ARCHITECTURE.md`). They still run as two sessions, so the
  design is built from the written `spec.md` and not from the planner's memory of the issue.
- The Implementer and the Tester are separate because a person (or model) testing their own
  code tends to test their own assumptions. The tester gets the acceptance criteria and the
  design, not the implementer's reasoning.

## Alternatives considered

- **One agent does everything.** Easiest to set up and nothing gets lost between steps. But
  that one session would be able to write everything, would review its own work, and would
  carry every failed attempt into the next one. The "check before moving on" rule would then
  depend on the agent being honest about itself.
- **One agent per stage (six agents).** Neat on paper, but stage 5 doesn't need a model, and
  making spec and design two different roles gains nothing when their rights are identical.
  More roles also means more prompts to maintain and more hand-offs where information can drop.
- **The implementer writes its own tests** (three roles). I tested this as a variant in
  experiment B (`experiment/variants.md`).

## Consequences

- Every role has a small tool policy that is easy to check (see ADR-005).
- Hand-offs become real files (ADR-003), which is what makes a run easy to follow on GitHub.
- The tester can write a test the implementer thinks is wrong, so there has to be a way to
  disagree: the implementer can answer `test_dispute`, which sends the work back to the tester
  once.
- More sessions means more prompt tokens than one long session. Prompt caching inside each
  session and the cheap model for the judge keep this in check, and I measure it.
