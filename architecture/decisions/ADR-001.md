# ADR-001: Four role agents, one per kind of permission, not one per stage

**Status:** Accepted (2026-11-15)
**Decision area:** D1, splitting the work

## Context

The workflow has six fixed stages. Each stage needs different inputs and, more
importantly, different *rights*: writing a spec or a design needs only read access,
implementing needs write access to source files, testing needs write access to test
files and the ability to run code, and reviewing must be independent of all of these.
Stage 5 (push the branch, open a PR, wait for CI) is mechanical: there is nothing for a
model to decide.

Two observations from A2 shaped this decision. First, the agent in A2 was most useful when
it was given a tightly scoped task with a clear acceptance check. Second, a single
long-running session accumulates context (tool output, failed attempts) that later stages
do not need and that makes the agent anchor on its first idea.

## Decision

Use **four agent roles** plus one non-agent LLM call:

| Role | Stages | Model | Write rights |
|---|---|---|---|
| Planner | 1 Requirements, 2 Design (two separate fresh sessions) | Sonnet 5.5 | none, returns structured output |
| Implementer | 3 Implementation | Sonnet 5.5 | source files named in `design.md` |
| Tester | 4 Testing | Sonnet 5.5 | `tests/test_autose_issue_N.py` only |
| Reviewer | 6 Review | Opus 5.5 | a scratch directory outside the repository |
| (testability judge) | check of stage 1 | Haiku 5.5 | none, no tools |

Stage 5 is plain code (the release step `st_release` in `orchestrator.py`), not an agent.

The split follows **permission boundaries**, not stage boundaries. Stages 1 and 2 share one
role because they need identical rights (read-only) and the same knowledge (repository
structure, `ARCHITECTURE.md`); they still run as two sessions so that the design is made
from the written `spec.md`, not from the planner's memory of the issue. The implementer and
the tester are different roles because a test written by the author of the code tends to
encode the author's assumptions; the tester sees the acceptance criteria and the design,
not the implementer's reasoning.

## Alternatives considered

- **One agent for everything.** Cheapest in setup and keeps all context, but the same
  session would hold write rights to everything and would review its own work; a failed
  attempt stays in context and biases the next one. It also makes the "check before
  moving on" rule depend on the agent's honesty.
- **One agent per stage (six agents).** Clean, but stage 5 does not need a model, and
  splitting spec and design into two *roles* buys nothing because their rights are the
  same. More roles also means more prompts to maintain and more hand-offs to lose
  information in.
- **Implementer writes its own tests** (three roles). Tested as a variant in experiment B
  (`experiment/variants.md`).

## Consequences

- Each role has a small, auditable tool policy (see ADR-005).
- Hand-offs become explicit files (ADR-003), which is what makes runs followable on GitHub.
- The tester can write a test that the implementer believes is wrong. We need a dispute
  path (implementer may answer `test_dispute`, which sends the work back to the tester once).
- More sessions means more prompt tokens than one long session; prompt caching within
  each session and the cheaper model for the judge keep this bounded. We measure it.
