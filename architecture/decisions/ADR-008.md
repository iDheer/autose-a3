# ADR-008: The reviewer is isolated by job, token, context and model, and argued out of approving by rules

**Status:** Accepted (2026-11-15)
**Decision area:** D8, reviewer independence

## Context

The reviewer must see only the issue, the diff and the repository at the PR head; it may run
code but not push. The main risk is not that it cannot find bugs but that it agrees too easily:
an LLM shown a confident explanation of a change tends to accept it, and a reviewer that
shares the implementer's model may share its blind spots.

## Decision

Isolation, layer by layer:

1. **Own job** (`review`) on a fresh runner, which checks out `refs/pull/N/head` itself with
   `persist-credentials: false`. Nothing from the build workspace is available.
2. **Own token:** the job has `permissions: contents: read` and nothing else. Posting the
   review is done afterwards by a different job (`publish`), so even a manipulated reviewer
   cannot comment, approve, push or merge.
3. **Own context:** prompt contains the issue (fenced as untrusted) and the diff; no spec,
   design, PR body or transcript (ADR-003).
4. **Own model:** Opus 5.5, while builders use Sonnet 5.5 (ADR-006).
5. **Own prompt and stance:** "find the reasons this PR should not be merged". It must
   (a) restate the issue's requirements in its own words, (b) run the full test suite, (c)
   write and run at least one probe of its own for the issue's main behaviour in its
   scratch directory, and (d) list risks it considered even when approving.

Anti-rubber-stamp rules, enforced in code by `publish.py`: an `approve` becomes
`request_changes` if any finding is `major` or `blocker`, if `checks_run` does not include a
full-suite run, or if any requirement in `requirement_checks` lacks evidence. The posted
review is a **COMMENT**-type review with the verdict in its body, never a formal GitHub
approval, so it can never satisfy branch protection on its own: a person must approve.

Calibration: five **seeded PRs** with known defects or known correctness
(`experiment/seeded_prs/`) measure how often the reviewer catches real problems and how
often it raises false alarms. Experiment A compares this isolated reviewer with an
"informed" reviewer that also sees the spec, the design and the implementer's PR description.

## Alternatives considered

- **Same job, separate agent session.** Cheaper, but the reviewer would share the working
  tree (and anything the implementer left in it) and the job token.
- **Reviewer sees the spec.** Lets it check spec compliance, but a wrong spec then produces a
  confident approval. The issue is the ground truth for the review.
- **Formal APPROVE review by the bot.** Would count towards branch protection and blur the
  "a person decides" rule.

## Consequences

- One extra job setup per review (about a minute).
- The reviewer can only discover the spec's interpretation from the code and tests, so it may
  flag deliberate scope decisions as missing features. We count these as false alarms in the
  results.
