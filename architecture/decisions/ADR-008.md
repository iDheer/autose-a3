# ADR-008: The reviewer is kept apart (own job, token, context and model), and rules stop it from approving too easily

**Status:** Accepted (2026-11-15)
**Decision area:** D8, reviewer independence

## Context

The reviewer may only see the issue, the diff and the repo at the PR head. It may run code but
must not push. The real danger isn't that it misses bugs, it's that it agrees too easily: show an
LLM a confident explanation of a change and it tends to accept it. And a reviewer that is the
same model as the implementer may share its blind spots.

## Decision

The reviewer is separated in five ways:

1. **Its own job** (`review`) on a fresh runner. It checks out `refs/pull/N/head` itself, with
   `persist-credentials: false`. Nothing from the build job's workspace is there.
2. **Its own token:** the job only has `permissions: contents: read`. Posting the review
   happens later, in a different job (`publish`). So even a manipulated reviewer can't comment,
   approve, push or merge.
3. **Its own context:** the prompt has the issue (marked as untrusted) and the diff. No spec,
   design, PR body or transcript (ADR-003).
4. **Its own model:** Opus 5.5, while the builders use Sonnet 5.5 (ADR-006).
5. **Its own instructions and attitude:** "find the reasons this PR should not be merged". It
   has to (a) restate the issue's requirements in its own words, (b) run the full test suite,
   (c) write and run at least one test of its own for the issue's main behaviour, in its scratch
   folder, and (d) list the risks it thought about, even when it approves.

**Rules against rubber-stamping**, enforced in code by `publish.py`: an `approve` becomes
`request_changes` if any finding is `major` or `blocker`, if `checks_run` doesn't include a
full-suite run, or if any requirement in `requirement_checks` has no evidence. The posted
review is a **COMMENT**-type review with the verdict in its text, never a formal GitHub
approval. So it can never satisfy branch protection by itself: a person has to approve.

**Calibration:** five **seeded PRs** whose defects (or correctness) I know in advance
(`experiment/seeded_prs/`) measure how often the reviewer catches real problems and how often
it raises false alarms. Experiment A compares this isolated reviewer with an "informed" one that
also sees the spec, the design and the implementer's PR description.

## Alternatives considered

- **Same job, separate agent session.** Cheaper, but the reviewer would share the working tree
  (and anything the implementer left in it) and the job's token.
- **Let the reviewer see the spec.** It could then check the spec was followed, but a wrong
  spec would lead to a confident approval. The issue is the truth the review is measured against.
- **Let the bot post a formal APPROVE review.** That would count towards branch protection and
  blur the "a person decides" rule.

## Consequences

- One extra job setup per review (about a minute).
- The reviewer can only work out how the spec interpreted the issue from the code and tests, so
  it may flag deliberate scope choices as missing features. I count those as false alarms in
  the results.
