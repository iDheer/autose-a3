# ADR-007: Checks are deterministic code wherever possible; an LLM judge only where the question is semantic; the orchestrator decides

**Status:** Accepted (2026-11-15)
**Decision area:** D7, checks

## Context

Each stage has a fixed check ("all acceptance criteria are testable", "the plan names the
files and functions", "the code builds", "all tests pass", "the PR is open and CI passes",
"the reviewer approves"). An agent saying "done, tests pass" is not evidence. Some checks are
mechanical; "testable" is partly semantic.

## Decision

The orchestrator runs every check itself, on the artifacts and on the working tree, and is
the only component that decides pass or fail.

| Stage | Check implemented as |
|---|---|
| 1 Requirements | **Mix.** Deterministic: ≥1 READY requirement; every acceptance criterion of every MUST/SHOULD requirement has non-empty Given/When/Then, no `<TBD`, no Appendix-A vague term; no open P1 question; spec verdict not `DRAFT`. LLM: Haiku judge rates each criterion testable/not with a reason. Pass = both. |
| 2 Design | **Deterministic.** Every file to modify exists; every function/class/method to modify exists in that file (AST lookup); files to create do not exist yet; every acceptance criterion id is mapped to at least one file and a test idea. |
| 3 Implementation | **Deterministic.** `git diff` is non-empty; only files declared in the design changed; `python -m compileall` and `import tinydb` succeed; `mypy tinydb` passes (CI runs mypy too). |
| 4 Testing | **Deterministic.** Full suite passes (JUnit XML); every acceptance criterion id has ≥1 test named after it; at least one new test **fails on the base commit** (otherwise the tests do not exercise the change). Run in a network-less namespace with a scrubbed environment. |
| 5 Release | **Deterministic.** `gh pr view` says OPEN; the dispatched CI run for the head SHA concluded `success`. |
| 6 Review | **LLM + rules.** Reviewer returns a structured verdict; `publish.py` overrides an `approve` to `request_changes` if any finding is `major`/`blocker`, if the reviewer did not run the test suite, or if it lists no evidence per acceptance requirement. |

When a check fails, the orchestrator writes the reason into that stage's artifact, and either
loops back (within budget) or stops the run.

## Alternatives considered

- **LLM judge for every stage.** Flexible, but slower, costs money every time, and is itself
  an agent that can be wrong or manipulated. Tests and AST lookups are free and exact.
- **Trust agent self-reports.** Cheapest, but the stage table requires a check *before*
  moving on; a self-report is not a check.
- **Deterministic-only stage 1.** Lexical rules cannot tell "returns the right documents" from
  "returns the documents in id order"; the judge catches criteria that are well-formed but
  not observable.

## Consequences

- The fail-before rule can reject legitimate refactor-only changes; none of our issues is a
  pure refactor, and the rule's failure message says so.
- The judge can be too strict; its verdict is logged per criterion so we can measure this.
