# ADR-007: Checks are plain code wherever possible, an LLM judge only for "is this testable?", and only the orchestrator decides

**Status:** Accepted (2026-11-15)
**Decision area:** D7, checks

## Context

Every stage has a fixed check: "all acceptance criteria are testable", "the plan names the files
and functions", "the code builds", "all tests pass", "the PR is open and CI passes", "the
reviewer approves". An agent saying "done, tests pass" proves nothing. Most of these checks are
mechanical; "testable" is partly a question of meaning.

## Decision

The orchestrator runs every check itself, on the artifacts and on the working tree, and it is
the only part of the system that says pass or fail.

| Stage | How the check works |
|---|---|
| 1 Requirements | **Both.** Code: at least 1 READY requirement; every acceptance criterion of every MUST/SHOULD requirement has a non-empty Given/When/Then, no `<TBD`, and none of the vague words from Appendix A; no open P1 question; the spec's verdict isn't `DRAFT`. LLM: the Haiku judge marks each criterion testable or not, with a reason. It passes only if both agree. |
| 2 Design | **Code.** Every file to change exists; every function/class/method to change exists in that file (checked with the AST); files to create don't exist yet; every acceptance criterion id is mapped to at least one file and a test idea. |
| 3 Implementation | **Code.** `git diff` isn't empty; only files named in the design changed; `python -m compileall` and `import tinydb` work; `mypy tinydb` passes (CI runs mypy too). |
| 4 Testing | **Code.** The full test suite passes (JUnit XML); every acceptance criterion id has at least one test named after it; at least one new test **fails on the base commit** (otherwise the tests don't actually test the change). Runs with no network and a cleaned environment. |
| 5 Release | **Code.** `gh pr view` says OPEN, and the CI run for the head commit ended in `success`. |
| 6 Review | **LLM plus rules.** The reviewer returns a structured verdict. `publish.py` turns an `approve` into `request_changes` if any finding is `major` or `blocker`, if the reviewer didn't run the test suite, or if it gives no evidence for some requirement. |

When a check fails, the orchestrator writes the reason into that stage's artifact and then
either loops back (if the budget allows) or stops the run.

## Alternatives considered

- **An LLM judge for every stage.** Flexible, but slower, costs money every time, and is itself
  an agent that can be wrong or manipulated. Tests and AST lookups are free and exact.
- **Trust what the agents say about themselves.** Cheapest, but the stage table demands a
  check *before* moving on, and an agent's own report isn't a check.
- **Only code checks for stage 1.** Word rules can't tell "returns the right documents" apart
  from "returns the documents in id order". The judge catches criteria that look well-formed
  but can't actually be observed.

## Consequences

- The "must fail on the base commit" rule could reject a pure refactor that is legitimate. None
  of our issues is a pure refactor, and the rule's failure message says this.
- The judge can be too strict. Its verdict is logged for every criterion, so I can measure how
  often that happens.
