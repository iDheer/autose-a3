# ADR-003: Agents hand over fixed-format files, and the raw issue stops at the spec

**Status:** Accepted (2026-11-15)
**Decision area:** D3, hand-offs

## Context

Every agent starts with a fresh context (ADR-001), so everything it needs has to be handed to
it on purpose. Give it too little and it has to rediscover, or make up, what earlier stages
already knew. Give it too much and it copies earlier reasoning, which is exactly what the
reviewer must not do. The issue text is untrusted (anyone can write it), so it also matters how
many agents read it directly.

## Decision

Agents return **structured output** (a JSON schema enforced by the Agent SDK's
`output_format`). The orchestrator validates it and **turns it into** the Markdown artifacts
itself. So agents never write artifact files, and every artifact looks the same on every run.

| Agent | Gets | Deliberately does not get |
|---|---|---|
| Planner (spec) | issue title, body and comments from trusted maintainers, inside an `<untrusted_issue>` block; the A1 skill as system prompt; read access to the repo | — |
| Planner (design) | `spec.md`, `ARCHITECTURE.md`, issue title, read access to the repo; on rework, the reviewer's *approach* findings | the issue body (the spec is now the contract) |
| Implementer | `spec.md`, `design.md`; on retry, the names of failing tests and the last 120 lines of pytest output; on rework, the reviewer's *code* findings | the issue body, the planner's reasoning, earlier implementation transcripts |
| Tester | the acceptance criteria from `spec.md`, the file and symbol list from `design.md`, read access to the repo (which includes the new code) | the implementer's summary and reasoning |
| Reviewer | issue title, body and maintainer comments, `git diff base...head`, the repo at the PR head | `spec.md`, `design.md`, the PR body, any transcript (ADR-008) |

Only two agents see the raw issue. The spec planner has to, and the reviewer has to judge
against what the user actually asked for, not against a spec that might be wrong.

## Alternatives considered

- **Pass whole transcripts or one shared conversation.** The most information, but mistakes
  travel forward, and anything injected into the issue reaches every agent.
- **Let agents write free-form Markdown.** Easier to prompt, but every check would have to
  parse prose. With a schema, "every acceptance criterion appears in the design" is a simple
  set comparison.
- **Give the implementer the issue too.** Handy, but then the issue becomes a second spec that
  competes with the real one. If the spec is wrong, the fix is to go back to stage 1, not to
  let the implementer quietly follow the issue instead.

## Consequences

- Anything the spec leaves out is lost for later stages. To limit this, the spec keeps a quote
  from the source for every requirement (the A1 provenance rules).
- Artifacts are stable and easy to diff and link to, which helps anyone following a run on
  GitHub.
- Changing a schema means changing the renderer code too, so I keep the schemas small.
