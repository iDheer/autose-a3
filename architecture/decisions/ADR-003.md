# ADR-003: Hand-offs are rendered artifacts with a fixed schema; the issue text stops at the spec

**Status:** Accepted (2026-11-15)
**Decision area:** D3, hand-offs

## Context

Every agent starts with a fresh context (ADR-001), so whatever it needs must be handed
over explicitly. Too little and the agent re-derives (or invents) what earlier stages knew;
too much and the agent anchors on earlier reasoning, which is exactly what the reviewer must
avoid. The issue body is untrusted input (anyone can write it), so the number of agents
that read it directly matters.

## Decision

Agents return **structured output** (JSON schema enforced by the Agent SDK's
`output_format`). The orchestrator validates it and **renders** the Markdown artifacts.
Agents therefore never write artifact files, and every artifact has the same shape on
every run.

| Agent | Receives | Deliberately does not receive |
|---|---|---|
| Planner (spec) | issue title, body and trusted-maintainer comments, inside an `<untrusted_issue>` fence; the A1 skill as system prompt; read access to the repository | — |
| Planner (design) | `spec.md`, `ARCHITECTURE.md`, issue title, repo read access, on rework the reviewer's *approach* findings | the issue body (the spec is the contract) |
| Implementer | `spec.md`, `design.md`, on retry the failing test names and the last 120 lines of pytest output, on rework the reviewer's *code* findings | the issue body; the planner's reasoning; earlier implementation transcripts |
| Tester | acceptance criteria from `spec.md`, file/symbol list from `design.md`, repo read access (which includes the new code) | the implementer's summary and reasoning |
| Reviewer | issue title, body and maintainer comments, `git diff base...head`, repository at the PR head | `spec.md`, `design.md`, PR body, any transcript (ADR-008) |

Only two agents see the raw issue: the spec planner (it must) and the reviewer (it must
judge against the original intent, not against a possibly wrong spec).

## Alternatives considered

- **Pass whole transcripts / a shared conversation.** Maximises information, but it
  propagates errors and lets injected text from the issue travel to every agent.
- **Free-form Markdown written by the agents.** Easier to prompt, but every check would
  have to parse prose. With a schema, "every acceptance criterion is mapped in the design"
  is a set comparison.
- **Give the implementer the issue too.** Convenient, but the issue then becomes a second,
  competing specification. When the spec is wrong, the fix is to go back to stage 1, not
  to let the implementer silently follow the issue instead.

## Consequences

- Information the spec drops is lost downstream. The spec keeps a source quote for every
  requirement (A1 provenance rules) to limit this.
- Artifacts are stable, diffable and linkable, which serves the "followable on GitHub" goal.
- Schema changes need code changes in the renderer; we keep schemas small.
