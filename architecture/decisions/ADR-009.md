# ADR-009: Several layers against prompt injection and runaway runs: no secret within an agent's reach, and budgets at three levels

**Status:** Accepted (2026-11-15). **Superseded in part by [ADR-011](ADR-011.md)** (2026-11-15):
the SDK's Bash sandbox did not start on the runner and was replaced by our own bubblewrap jail.
**Decision area:** D9, safety and failures

## Context

Anyone with a GitHub account can open an issue on a public fork, and that issue is read by an
agent that can edit code and run it. The code the agent writes is then run by tests in CI.
Separately, agents can loop, get stuck or burn money. GitHub Actions also has limits that shape
the design: a `GITHUB_TOKEN` can't trigger other workflows except through
`workflow_dispatch`/`repository_dispatch`, jobs time out, and a concurrency group keeps only one
waiting run.

## Decision

**Who can start a run** is limited (ADR-010). An outsider's issue is only processed after a
maintainer labels it or comments `/autose`. That's the first and strongest layer. Everything
below assumes a maintainer might still label a malicious issue by mistake.

**Handling untrusted text.**
- Issue text never reaches a shell. The workflow never pastes `${{ github.event.* }}` text into
  `run:` scripts; Python reads it from `$GITHUB_EVENT_PATH` instead.
- In prompts, issue text sits inside an `<untrusted_issue id=NONCE>` block with a random
  nonce, and the system prompt says it is data, never instructions.
- Only the spec planner and the reviewer see the raw issue (ADR-003).

**Nothing worth stealing within reach.**
- The API key never goes into an agent process. Agents talk to a **local proxy that adds the
  key** (`ANTHROPIC_BASE_URL=http://127.0.0.1:PORT`, with a dummy key). So child processes,
  such as pytest or code the agent wrote, can't read the key either.
- `GITHUB_TOKEN` is removed from the environment before agents start, and checkouts don't
  keep credentials.
- ~~Agent Bash runs sandboxed without network~~ *(superseded by ADR-011: our own bubblewrap
  jail instead of the SDK sandbox)*. The orchestrator's own checks run tests inside
  `unshare --net` with a cleaned environment.
- Before anything is pushed: the diff is scanned for secrets (exact matches on known secret
  values, plus the patterns `sk-ant-`, `ghp_`, `ghs_`, `github_pat_`). Changes to `.github/`,
  `.autose/` or files outside the design are rejected. A `GITHUB_TOKEN` can't push workflow
  changes anyway.

**Budgets at three levels.**
- Per agent call: `max_turns`, `max_budget_usd` (ADR-006) and a 15-minute wall-clock timeout
  (`asyncio.wait_for`).
- Per run: an 8 USD cost cap and the attempt counters (ADR-002).
- Per job: `timeout-minutes` (build 60, review 30, the others 10).

**When a stage gets stuck or fails.** Every stop, whether it's a failed check, a used-up budget,
a timeout or a crash, writes the reason into that stage's artifact, posts a comment on the issue
with links, adds the label `autose:stopped`, and keeps all artifacts. A `finally` block in the
orchestrator makes sure the store is always pushed.

## Alternatives considered

- **Trust the model to resist injection.** Needed, but not enough on its own.
- **Give the API key straight to the agent** (the usual setup). Simpler, but then any test the
  agent writes can read the key and, with network access, send it anywhere. That's the biggest
  single risk in this design, so it gets the most expensive fix.
- **Only process issues from collaborators.** Too strict: the whole point is to handle real
  users' issues once a maintainer has looked at them.

## Consequences

- The proxy is extra code that everything depends on: if it breaks, every agent breaks. It has
  a unit test with a fake upstream.
- The secret scan can't catch a secret that is encoded and hidden inside a committed file. What
  prevents live leaking is that the sandbox has no network. The remaining risk is listed in the
  report.
