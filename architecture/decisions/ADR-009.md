# ADR-009: Defence in depth against prompt injection and runaway runs: no secret in reach of an agent, budgets at three levels

**Status:** Accepted (2026-11-15)
**Decision area:** D9, safety and failures

## Context

Anyone with a GitHub account can open an issue in a public fork, and the issue text is read
by an agent that can edit code and run it. Code that the agent writes is executed by tests in
CI. Separately, agents can loop, stall or burn money, and GitHub Actions has limits that
change how a workflow can be built (a `GITHUB_TOKEN` cannot trigger other workflows, except
via `workflow_dispatch`/`repository_dispatch`; jobs time out; concurrency groups keep only one
pending run).

## Decision

**Who can start a run** is restricted (ADR-010), so an outsider's issue is only processed
after a maintainer labels it or comments `/autose`. That is the first and strongest layer;
the rest assumes a maintainer may label a malicious issue by mistake.

**Untrusted text handling.**
- Issue text never reaches a shell: the workflow never interpolates `${{ github.event.* }}`
  text into `run:` scripts; Python reads `$GITHUB_EVENT_PATH`.
- In prompts, issue text sits in an `<untrusted_issue id=NONCE>` block with a random nonce,
  and the system prompt says it is data, never instructions.
- Only the spec planner and the reviewer see the raw issue (ADR-003).

**Nothing worth stealing in reach.**
- The API key never enters an agent process: agents talk to a **local key-injecting proxy**
  (`ANTHROPIC_BASE_URL=http://127.0.0.1:PORT`, dummy key). Child processes (pytest, code the
  agent wrote) therefore cannot read the key either.
- `GITHUB_TOKEN` is removed from the environment before agents start; checkouts do not
  persist credentials.
- Agent Bash runs sandboxed without network; orchestrator checks run tests inside
  `unshare --net` with a scrubbed environment.
- Before any push: secret scan of the diff (exact match on known secret values plus
  `sk-ant-`, `ghp_`, `ghs_`, `github_pat_` patterns); changes to `.github/`, `.autose/` or files
  outside the design are rejected. A `GITHUB_TOKEN` cannot push workflow changes anyway.

**Budgets at three levels.**
- Per agent call: `max_turns`, `max_budget_usd` (ADR-006) and a wall-clock timeout
  (`asyncio.wait_for`, 15 minutes).
- Per run: 8 USD cost cap; attempt counters (ADR-002).
- Per job: `timeout-minutes` (build 60, review 30, others 10).

**Stuck or failed stages.** Every stop, whether a check failure, an exhausted budget, a
timeout or an exception, writes the reason into that stage's artifact, posts a comment on the
issue with links, labels it `autose:stopped`, and keeps all artifacts. A `finally` block in
the orchestrator guarantees the store push.

## Alternatives considered

- **Rely on the model's injection resistance.** Necessary, not sufficient.
- **Pass the API key directly to the agent** (the usual setup). Simpler, but then any test
  the agent writes can read the key and, with network, send it anywhere. That is the single
  biggest risk in this design, so it gets the most expensive mitigation.
- **Run only on issues from collaborators.** Too restrictive: the point is to process real
  users' issues, after a maintainer has looked at them.

## Consequences

- The proxy is extra code on the critical path; if it breaks, every agent breaks. It has a
  unit test with a fake upstream.
- The secret scan cannot catch an encoded exfiltration inside a committed file; the
  network-less sandbox is what prevents live exfiltration. Residual risk is listed in the
  report.
