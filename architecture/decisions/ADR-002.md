# ADR-002: Plain code decides the flow; separate Actions jobs mark where trust changes

**Status:** Accepted (2026-11-15)
**Decision area:** D2, control flow

## Context

The flow has loops. If tests fail, the work goes back to implementation. If tests keep failing,
it goes back to design. And the review can send the work back to design or implementation, at
most twice. GitHub Actions jobs can't loop: they form a fixed graph. I could let an LLM decide
what happens next, which is flexible, but anyone can write an issue, and whatever reads that
issue could be talked into skipping a check.

## Decision

- Stages 1–5 run inside **one Actions job** (`build`), driven by `orchestrator.py`, which is a
  plain Python state machine. Its states are the six stages plus `STOPPED` and `HANDOVER`.
  It moves between states only based on check results and budget counters.
- **Agents can ask for a jump, but only the code can make it.** The implementer can return
  `design_gap` (asking to go back to stage 2) or `test_dispute` (asking stage 4 to look at a
  test again). The orchestrator only says yes if the budget allows it.
- Stage 6 runs in **separate jobs** (`review`, then `publish`). These job boundaries are about
  trust, not about flow: the reviewer gets its own token, its own fresh checkout, and no access
  to the build job's files.
- The review loop works by **starting the workflow again**: `publish` triggers
  `workflow_dispatch` with `mode=rework`, `from_stage=design|implement` and `round=k+1`. The
  reviewer's structured verdict says where to go back to, and `publish.py` checks that
  against the round budget.

Budgets (in `.autose/config.toml`): 3 implementation attempts per design, 1 design revision
caused by tests, 1 test dispute, and 2 review send-backs (so at most 3 reviews).

## Alternatives considered

- **An LLM orchestrator directing worker agents.** Rejected. Its choices change from run to
  run, it is harder to audit, and a prompt-injected orchestrator could skip checks. The
  assignment fixes the flow anyway, so the extra flexibility would mostly be a risk.
- **One Actions job per stage, chained with `needs`.** Rejected. Jobs can't loop, each one
  spends about a minute on setup (checkout, Python, pip), and state would have to be passed
  between every step as artifacts.
- **Everything, including the review, in one job.** Rejected. The reviewer would share files,
  environment and token with the implementer, which breaks ADR-008.

## Consequences

- I can test the whole flow without a model: `orchestrator.py` has a fake-agent mode that I
  used to try every transition before spending any tokens.
- Each review round costs a new workflow run (about 1–2 minutes of setup). That's fine for at
  most two rounds.
- Because each round is a new run, state has to be saved between runs (ADR-004).
