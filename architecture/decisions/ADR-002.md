# ADR-002: A deterministic state machine in code controls the flow; Actions jobs mark trust boundaries

**Status:** Accepted (2026-11-15)
**Decision area:** D2, control flow

## Context

Stages 3 and 4 loop (tests fail, go back to implementation), stage 4 can escalate to stage 2
(tests keep failing), and stage 6 can send work back to stage 2 or 3 at most twice. GitHub
Actions jobs form a static DAG: they cannot loop. An LLM "planner" that decides what to do
next is flexible, but anyone can write an issue, so whatever reads the issue can be
manipulated into skipping a check.

## Decision

- Stages 1–5 run inside **one Actions job** (`build`) driven by `orchestrator.py`, a
  plain Python state machine. States are the six stages plus `STOPPED` and `HANDOVER`.
  Transitions depend only on check results and budget counters.
- **Agents can request a transition but never take it.** The implementer may return
  `design_gap` (asks for stage 2) or `test_dispute` (asks for stage 4 to revisit a test). The
  orchestrator grants the request only if the budget allows it.
- Stage 6 runs in **separate jobs** (`review`, then `publish`). These job boundaries are
  trust boundaries, not control flow: they give the reviewer its own token, its own fresh
  checkout and no access to the build workspace.
- The review loop is implemented by **re-entering the workflow**: `publish` triggers
  `workflow_dispatch` with `mode=rework`, `from_stage=design|implement` and `round=k+1`.
  The routing decision (design vs. implementation) comes from the reviewer's structured
  verdict, and `publish.py` validates it against the round budget.

Budgets (in `.autose/config.toml`): 3 implementation attempts per design, 1 design
revision triggered by tests, 1 test dispute, 2 review send-backs (so at most 3 reviews).

## Alternatives considered

- **LLM orchestrator with worker agents.** Rejected: non-deterministic, harder to audit, and
  a prompt-injected orchestrator could skip checks. Our flow is fixed by the assignment, so
  the planner's flexibility would mostly be a liability.
- **One Actions job per stage, chained by `needs`.** Rejected: no loops, about a minute
  of setup (checkout, Python, pip) per job, and state would have to be passed through
  artifacts at every step.
- **Everything, including review, in one job.** Rejected: the reviewer would share the
  filesystem, environment and token with the implementer, which breaks ADR-008.

## Consequences

- The control flow is testable without a model: `orchestrator.py` has a fake-agent mode
  that we used to exercise every transition before spending tokens.
- A review round costs a new workflow run (about 1–2 minutes of setup). Acceptable for at
  most two rounds.
- Because a new run starts per round, state between runs must be persisted (ADR-004).
